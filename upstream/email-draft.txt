Hi,

xf86HandleColormaps() allocates the per-screen PreAllocIndices scratch
array using the driver-supplied maxColors argument, but nothing sizes or
validates that argument against the visuals the screen actually has.
Meanwhile CMapAllocateColormapPrivate() sizes a colormap from
pVisual->ColormapEntries whenever CMapColormapUseMax() is true, and both
CMapReinstallMap() and CMapStoreColors() fill PreAllocIndices with that
many entries:

    int i = cmapPriv->numColors;            /* pVisual->ColormapEntries */
    int *indices = pScreenPriv->PreAllocIndices;   /* int[maxColors] */
    while (i--)
        indices[i] = i;                     /* writes past the array */

If a driver follows the historical convention and passes maxColors = 256
while the screen exposes a visual with more colormap entries, this is a
deterministic, repeatable heap overflow.

We hit this in a clean-room DDX written against current X.Org: fb built a
depth-32 DirectColor visual with ColormapEntries = 2048, the driver passed
256, and installing that colormap (any X client can do it with
XCreateColormap + XInstallColormap — opening a terminal did it) overflowed
the 1 KB allocation by exactly 7168 bytes. The corruption happened to land
on an ExtensionEntry, so the crash looked like a bad request dispatch and
was painful to trace. Valgrind + a hardware watchpoint found the writer.

The same wall was hit driver-side on depth 30 (indices up to 1023 vs 256):
https://www.spinics.net/lists/amd-gfx/msg06445.html
and modesetting sidesteps the related depth>24 LUT problem by not calling
xf86HandleColormaps() at all:
https://lists.freedesktop.org/archives/xorg-devel/2018-February/055867.html

Since a local unprivileged X client can trigger the overflow repeatedly
and the data written is a fixed sequential pattern (pointers become
non-mappable low addresses, but lengths/indices/flags get corrupted), it
is at least a reliable remote-for-a-local-client DoS of a possibly
privileged server, and a constrained heap-corruption primitive otherwise.

The patch below keeps every existing semantic and only sizes the scratch
array from the screen's actual visuals, warning when the driver
underreported. It applies to current master (verified the code is
unchanged there).

+    /* CMapAllocateColormapPrivate sizes a colormap from

+                       "the largest visual colormap size (%d); growing "
+                       "PreAllocIndices\n", maxColors, indicesNeeded);
